## The short version

- **Tracing never raises into your code.** If Avaliar is down, slow, or rejects a trace, your traced function still returns normally. Problems are logged once on the `avaliar` logger.
- **Blocking can raise**, on purpose: `PromptBlockedError` when a prompt is blocked, and `AvaliarDetectionUnavailableError` when you chose `fail_closed=True` and the prompt could not be checked.
- **Every request has a timeout.** A hung backend can never hang your app.

## Errors

All SDK errors inherit from `AvaliarError` and can be imported from `avaliar`.

```
AvaliarError
├── AvaliarAPIError                    # 5xx from Avaliar
├── AvaliarRequestTimeout              # Avaliar did not answer in time
├── AvaliarConnectionError             # Avaliar could not be reached
├── AvaliarRateLimitError              # 429
├── AvaliarDetectionUnavailableError   # prompt not checked, fail_closed=True
├── PromptBlockedError                 # prompt blocked (blocking=True)
└── AvaliarUserError                   # the request itself is wrong (4xx)
    ├── AvaliarAuthError               # 401: bad or revoked API key
    ├── AvaliarPermissionError         # 403: e.g. a plan limit; .code says why
    ├── AvaliarNotFoundError           # 404
    ├── AvaliarConflictError           # 409
    └── AvaliarConfigError             # SDK not configured, e.g. no API key
```

Error messages carry the server's explanation, for example `403: Cloud detection requires a Pro plan.`

## PromptBlockedError

Raised by a `blocking=True` function when Avaliar blocks the prompt. The model is not called.

```python
from avaliar import traceable, PromptBlockedError

@traceable("llm", blocking=True)
async def generate(messages): ...

try:
    result = await generate(messages)
except PromptBlockedError as e:
    e.reason           # "Blocked: prompt_injection (97%)"
    e.issues           # detected issues, possibly empty
    e.blocked_message  # the workspace's reply text, or None
```

To get the reply text returned instead of an exception, use `on_block="reply"`. See [Blocking mode](/sdk/detection#blocking-mode).

## AvaliarDetectionUnavailableError

Raised only with `fail_closed=True`, when the prompt could not be checked: Avaliar was unreachable, timed out, or its detection service was down. The model is not called. Without `fail_closed`, these calls go through unchecked and one warning is logged.

## Retries

| Failure | Retried? |
|---------|----------|
| Connection error, timeout, 429, 5xx | Yes, up to 3 attempts with backoff (traces) |
| 4xx (bad key, plan limit, invalid data) | No: it will not fix itself |

The blocking prompt check is held to `blocking_timeout` (default 10s) in total. It is not retried on timeout, only once on a dropped connection.

## Timeouts

| Variable | Default | Applies to |
|----------|---------|-----------|
| `AVALIAR_TIMEOUT` | `10` | Sending traces |
| `AVALIAR_BLOCKING_TIMEOUT` | `10` | The blocking prompt check (or `blocking_timeout=` per function) |
| `AVALIAR_FLUSH_TIMEOUT` | `5` | Sending queued traces at process exit |

## Making sure traces are sent

Traces go through a background queue. Normal processes flush it at exit. Serverless handlers and batch jobs should flush explicitly:

```python
import avaliar

def handler(event, context):
    result = run_agent(event)
    avaliar.flush(timeout=5)   # True when everything was sent
    return result
```

## Seeing what went wrong

```python
import logging
logging.basicConfig()
logging.getLogger("avaliar").setLevel(logging.INFO)
```

Each distinct problem (a missing key, a rejected trace, a prompt that could not be checked) is logged once rather than once per span.
