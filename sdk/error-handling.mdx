The guard is built never to break your app. A check returns a `Decision`; it does not raise for a block, for a model that failed, for a deep check that timed out, or for evidence that could not be written.

Only three errors are ever raised, and two of them only when you ask:

| Error | When | Carries |
|---|---|---|
| `AvaliarPolicyError` | The policy is invalid, at `Guard(...)` construction (or `guard.add_examples` with an unknown category). Never per check. | `source`, `line`, `field` |
| `GuardBlocked` | A check blocks and you asked for an exception: `d.raise_for_block()`, `Guard(raise_on_block=True)`, or `@guard.tool` (by default) | `decision` |
| `GuardUnavailable` | A check could not complete, the checkpoint is `on_error: fail_closed`, and `raise_on_block=True` | `decision` |

All three subclass `AvaliarError`. `AvaliarPolicyError` is also a `ValueError`.

```python
from avaliar import AvaliarPolicyError, Guard, GuardBlocked

try:
    guard = Guard()
except AvaliarPolicyError as e:
    print(e.source, e.line, e.field, e)     # avaliar.yaml 12 input.rules.prompt injection.action ...
    raise

d = guard.check_input(message)
if d.blocked:
    return d.reply

try:
    guard.check_tool_call("send_email", args).raise_for_block()
except GuardBlocked as e:
    log.info("blocked: %s", e.decision.reasons)
```

`raise_for_block()` raises for `block` and for `approve` (a decision still waiting for a person), and returns the decision otherwise, so it chains.

## Faults inside the guard

A detector, a model or the deep check that fails is caught inside the guard and recorded. The categories it was meant to score are listed in `d.not_evaluated` with a reason (`error`, `judge_unavailable`, `budget` and others), and never counted as clean. What happens next is the checkpoint's `on_error` in the policy:

| `on_error` | Effect |
|---|---|
| `fail_open` (default) | The decision is made from what could be scored; the gap is recorded |
| `fail_closed` | The check blocks when a category whose rule would block or ask for approval could not be evaluated |

```yaml
input:
  on_error: fail_closed
```

Rules that fire still decide as usual. If the guard cannot even apply its rules or write back a redaction, it blocks rather than hand back text a rule wanted changed.

## Budgets

Each checkpoint has a time budget (`budget_ms`). Categories that could not finish in time are `not_evaluated` with reason `budget`, and `on_error` applies. The deep check gets `judge.timeout_ms` on top unless `judge.within_budget: true`. After repeated deep check failures a circuit breaker stops calling it for a while, so an outage does not slow every check.

## Evidence

Evidence is written off the request path. A failed write logs a warning and sets `d.evidence_ok = False`; it never raises. With `evidence.required: true` the write is synchronous, a failure is recorded as `not_evaluated` (`evidence_write_failed`), and with `on_error: fail_closed` the check blocks.

## Avaliar Cloud

The cloud link never breaks checking. Uploads run on a background thread; an outage, a timeout or a refused batch leaves the records on disk to upload later, and is logged. See [Connecting to Avaliar Cloud](/sdk/cloud).

## Logging

Problems that need you are logged once to the `avaliar` logger at warning level: an invalid policy key with a warning, evidence that cannot be written, an unreachable deep check, a refused upload.
